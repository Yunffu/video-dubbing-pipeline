# 复盘与迭代记录

> 对应用户第 4 点：「我出成果 → 你复盘（断句？口型？翻译腔？）→ 改 Prompt / 改 Pipeline → 一起重新迭代」。
>
> 一轮 = **① 出题（成片+指标+成本）→ ② 人判 → ③ 归因 → ④ 改哪段代码/Prompt → ⑤ 改后指标与成本 → ⑥ 是否回归**。
> 本文件按这个格式记录，**每一轮都留痕**。

## R1：指标口径错误 → 整轮结论作废

- **触发**：字幕擦除初版跑分，「M1_04 只差 0.13dB 到 30dB 阈值」。
- **人判**：我自己复核数字时发现同一条 case 换采样帧数，PSNR 在 16.07 / 29.89 / 26.46 / 16.09 之间跳。
- **归因**：**我们的口径 bug**（第四类）。主指标用了采样帧均值，而素材里有近黑帧
  （母版整帧均亮度≈0），黑帧擦完还是黑 → 与母版逐像素相同 → **PSNR 恒 99dB**，把均值拉飞。
- **改了什么**：`eval/metrics.py::subtitle_erase_in_memory` 改中位数 + 近黑帧剔除并计数 +
  报 p25/p75；`scripts/erase_sweep.py` 同步改口径；`eval/runner.py` 加
  `metric_profile` 指纹，跨 run 比较时校验口径一致。
- **改后**：4/6/8/12 帧的中位数稳定在同一区间，采样数不再影响结论。
- **回归**：全量重跑，口径指纹从 v1 切到 `median_v2_blackskipped`；
  runner 明确提示「两轮口径不同 → pass/fail 不可直接比」。

## R2：参数扫描结论整条作废

- **触发**：R1 之后重跑 `erase_sweep.py`（16 组配置）。
- **归因**：口径修正的**连带后果**。
- **旧结论**：「mask 边界落在字上会崩（18.7dB），余量 ≥12 行就稳（29.5–30dB），
  启发式 vs oracle 差 0.9dB」。
- **新结论（中位数口径，24 帧）**：全部 16 组配置落在 **15.6–16.1 dB**，
  余量 4/12/24/40 的差别 <0.5dB，启发式 vs oracle 差 **0.03dB**。
  → **「mask 边界放在哪、余量给多少」根本不是杠杆**；旧结论是被近黑帧造出来的假规律。
- **改了什么**：文档 `10-选型结论与badcase清单.md` §2.3 整节重写，两版数字并列。
- **回归**：结论反转本身已写进文档，不隐藏。

## R3：把「该优化什么」问成一道可测的题

- **触发**：既然余量不是杠杆，那杠杆是什么？
- **做法**：`scripts/erase_compare.py` —— **一次只动一个变量**的 2×2：
  引擎 {OpenCV 边缘扩散, LaMa 内容感知} × mask {全宽横带, 逐文字像素(oracle)}，
  外加「挖大洞」的引擎健全性负控（`scripts/engine_sanity.py`）。
- **新增口径**：**字形像素 PSNR**（`eval/metrics.py::psnr_mask`）——
  只在字幕字形像素上算，因为字幕区 93% 是干净背景，会稀释字形上的误差。
- **结论**：mask 粒度 **+6.6dB**（两条 case 一致）；引擎 **0~+2dB**。
  → 优先级：**先做逐文字 mask，再选引擎**。最优组合 LaMa + 逐文字 mask（M1_01：24.66dB / SSIM 0.930）。
- **回归**：结论与 R2 一致（整带 inpaint 到不了 30dB），无冲突。

## R4：「LaMa 不支持细笔画」——**我的结论是错的**

- **触发**：R3 里有一格异常：`lama + 逐文字 mask` 只有 10.46dB，比 OpenCV 差 8dB。
  我当时的判断是「LaMa 是大洞模型，细笔画 mask 它补不了」→ **写进了结论**。
- **人判（我自己）**：这个格子和其它格子差得太多，且**指标恰好等于「什么都不做」的基线**
  （5.88dB，Δ=0.00）—— 一个模型不可能精确等于基线，**这更像「模型根本没跑」**。
- **最小证伪实验**：绕开自己的封装，直接把 512×512 的 tile 和稀疏笔画 mask 喂给 ONNX 图
  → 模型改了 **90.91%** 的像素。**模型没问题，是我们的封装有问题。**
- **归因**：**我们的代码 bug**。512 高的纵向窗口按 mask 的 `ys.min()/ys.max()` 定位，
  而 oracle mask 混入了重编码噪点 → 窗口落在 rows 289–801，**真正的字幕行（~940–1010）在窗口外**
  → 每个瓦片里都没有洞 → 模型原样返回 → 输出与输入逐像素相同。
- **改了什么**：① `pipeline/inpaint/lama_onnx.py::_row_runs()`：按 mask 的**连续行段**
  合并成文本行组再开窗口（多行字幕 → 多窗口），噪点组按像素数剔除；
  ② `scripts/erase_compare.py::text_pixel_mask()`：oracle mask 加**连通域面积过滤**，
  只留字形笔画、丢掉孤立噪点。
- **改后**：mask 内被修改像素 **0% → 99.7%**；同一格 **10.46 → 22.68 dB**；
  M1_01 同一格 **5.88 → 19.92 dB**（字形 PSNR）。
- **回归**：两条 case 的 2×2 全部重跑，四格结论一致（mask 粒度仍是主要矛盾）。
- **留下的教训**（写进 `09-抗压与失败归类.md` §3.4）：
  **「模型不支持 X」这种结论，必须先用一个不经过自己封装的最小实验去证伪。**
  指标异常到「恰好等于基线」这种程度时，先怀疑自己。

## R5–R6：等人评的轮次（工具已就绪）

R5（字幕擦除观感）与 R6（译制质量：断句 / 口型 / 翻译腔）的**出题部分已经做完**：

```bash
# 出题：成片 + 指标 + 成本，一份待评清单
python eval/human_review/make_items.py --cases all
python eval/human_review/build_packet.py build \
       --items results/human_review/items/items.json \
       --out results/human_review/packet.json

# 人判：看片 → 填 results/human_review/reviews.json
#   字段：erase / break / lip / style / sub / overall（1–5 分，5=最好）

# 复盘：反推阈值 + 算「达标的那部分花了多少钱」
python eval/human_review/build_packet.py summarize \
       --packet results/human_review/packet.json \
       --reviews results/human_review/reviews.json \
       --out results/human_review/thresholds.json
```

`make_items.py` 已生成 8 条（4 条 case × 底部/压脸两种），每条含：

- 成片 mp4（`results/human_review/items/`，可由脚本重建，未入库）
- 自动指标：字幕区 PSNR（含 p25/p75）、SSIM、baseline、Δ、区外 99dB
- 成本：本环节为 0（无模型调用）；译制环节成本走 `eval/cost.py`

**`summarize` 的输出就是下一轮要改的东西**：

| 输出 | 含义 | 怎么用 |
|---|---|---|
| `metric_thresholds` | 每个指标上的「阈值候选」+ 是否可分 | 把候选值写回 `spec/subtitle_erase.yaml`，**并注明来源=人评** |
| `cost.good_usd` / `cost.bad_usd` | 达标样本花了多少 / 不达标样本花了多少 | 达标成本 = 降本的**上限目标**；不达标花的钱 = 该砍掉的 |
| `bad_samples` | 人判不可接受的样本 | 拉进 badcase 清单做归因 |

> ⚠️ 现在 `results/human_review/reviews.simulated.json` 里是**模拟打分**（我按指标自动填的），
> 只用来验证「打分 → 反推阈值」这条链路是通的（`separable` 标记会告诉你哪个指标真能分开好坏）。
> **它不是你的判断，不能当结论引用。** 真人打分请填 `reviews.json`。

## 迭代记录模板（后续每轮照抄）

```markdown
### R<n>：<一句话标题>
- **触发**：谁发现了什么（用户看片 / 指标异常 / 故障注入）
- **人判**：原话 + 打分（哪条 case、哪个维度、几分）
- **归因**：模型不行 / 素材不可解 / 环境限制 / **我们的代码 bug**
- **改了什么**：具体文件与函数（不是「优化了一下」）
- **改后**：指标 + 成本 + 耗时 的前后对比（带口径）
- **回归**：本来 PASS 的 case 是否还 PASS（`eval/runner.py --baseline`）
- **有没有留下未解决的**：明确写
```
