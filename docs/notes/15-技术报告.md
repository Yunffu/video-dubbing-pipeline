# 技术报告：多语言视频译制流水线的评测与验收系统

> 日期：2026-11-25　｜　项目：`video-dubbing-pipeline/`　｜　目标岗位：B站「AI 应用研发实习生（视频译制/多模态）」
>
> **本报告的纪律**（贯穿全文）：
> 1. 每个数字都能指到**一条可复跑的命令 + 一个口径**；
> 2. 阈值必须注明**来源**（实测 / 人评 / 硬约束），没有来源的阈值一律标「初版」；
> 3. 做过的说「已做」，没做的说「没做」，做错的**留在文档里不删**（见 §12）；
> 4. 素材有版权红线，只用可再分发的源或自建派生件。

## 0. 摘要

**问题**：视频译制的 Pipeline 不难写（ASR / 翻译 / TTS 都是现成 API，agent 一晚上能拼出 demo），
**难的是让它的产出敢交付**。判断「这版擦干净了吗 / 比上版好吗 / 花了多少钱 / 会不会挂」
——这四问需要标准、需要数据、需要留痕，而这恰恰是 AI 写不出来的部分。

**做法**：把 Pipeline 当**被测对象**，把评测与验收当**作品本体**。五层结构：

| 层 | 职责 | 落地 |
|---|---|---|
| L1 素材层 | 可复现的素材与 GT | 4 母版 + 20 case + 5 场景素材，SHA256 确定性重建；**合成 GT 法**（母版即 GT） |
| L2 标准层 | 每个环节的契约与阈值 | `spec/*.yaml` 七份（六个环节 + `_fault.yaml`），阈值注明来源 |
| L3 实现层 | 被测对象 | `pipeline/`（asr / translate / tts / subtitle_erase / inpaint / compose / gateway） |
| L4 评测层 | 跑分、回归、成本、人评 | `eval/`（runner / metrics / cost / human_review） |
| L5 约束层 | 抗压、降级、审计、复盘 | `pipeline/runtime/`、`pipeline/gateway/`、`docs/notes/12-复盘与迭代记录.md` |

**结果**（细节见各章）：

- 端到端：4 个真实场景跑出成片（中→英配音 ×2、英→中配音 ×2），真实调用 DeepSeek 4 次，**无一次降级**
- 字幕擦除：8/8 通过硬约束（区外 Δ=0.0 dB，误伤**可证**），但 8 条全部 WARN 未达调优档
- 选型：一次只动一个变量的对照实验证明**瓶颈在 mask 粒度（+6.6 dB），不在引擎（0~+2 dB）**
- 抗压：7/7 故障注入 PASS（断网 / 401 / 429 / 5xx / 媒体损坏 → 降级 + 留痕，**不挂**）
- 接入层：网关五职责实现并本地 mock 验证（38 ms / 0 ms / 153 ms / 58.9 s 四种行为）
- 成本：翻译 $0.00019 / 1.98 分钟音频；**反事实证明成本大头是 ASR+TTS（283×）**
- 复盘：R1–R6 逐轮留痕，含**一次结论反转**与一次「我的结论是错的」

**缺口**（详见 §14）：人评未打分、长片未端到端、动画画风未覆盖、口型明确不做。

## 1. 素材与 GT：合成 GT 法

译制评测最麻烦的是**没有标准答案**——你擦掉的字幕没有「正确画面」可比。

我们的做法：**母版 = GT，派生件 = 母版 + 烧录字幕**。

```
assets/raw/M1_01.mp4            母版（干净，可再分发）
        │  scripts/make_derived.py（libx264 crf 20 烧录字幕）
        ▼
assets/derived/M1_01_hard_sub_bottom.mp4   派生件（带硬字幕）
        │
        └─ 两者相减 = 字幕像素的**精确位置**（oracle mask）
```

于是有了三层可测的东西：

| 层 | 指标 | 含义 |
|---|---|---|
| 擦除前 | `psnr_baseline`（派生件 vs 母版） | **重编码天花板**——不擦字幕也就这个水平 |
| 擦除后 | `psnr_in_mask`（擦后 vs 母版） | 绝对水平 |
| 净收益 | `delta = after − baseline` | **唯一可比的口径**：我们比的是「比不擦好多少」 |

> 没有 baseline 的绝对 PSNR 是没有意义的数字。这也是为什么报告里每个擦除数字都带 Δ。

**素材来源与版权**：4 条母版（M1_01 / M1_02 / M1_04 / M3_01）全部来自 Wikimedia Commons，
许可与 SHA256 登记在 `assets/manifest.json`；仓库**只留 manifest + meta + cases**，
母版与派生件由脚本按 SHA256 确定性重建。**没有使用 B站原片作为素材**（版权红线，见 §13）。

**case 集**：20 条 = 4 母版 × 5 类难例（hard_sub_bottom / hard_sub_face / low_bitrate / noisy / mouth_occluded）。

```bash
python scripts/audit_assets.py     # 口径 --frames 24
```

## 2. 指标口径纪律（这一章是整个项目的技术内核）

评测系统的价值不在于「算出多少分」，而在于**这个分数换一批采样就不变**。
我们在这上面付了两次学费，两次都写进了文档（§12 R1、R2）。

### 2.1 教训一：均值 + 近黑帧 = 结论随采样数漂移

现象：同一条 case 换采样帧数，PSNR 在 **16.07 / 29.89 / 26.46 / 16.09 dB** 之间跳。

归因：母版里有**近黑帧**（整帧均亮度 ≈ 0）。黑帧擦完还是黑 → 与母版逐像素相同 → **PSNR 恒 99 dB**
→ 均值被这几帧拉飞。素材没问题，是**我们的口径 bug**。

修法（`eval/metrics.py::subtitle_erase_in_memory`）：
- 主指标改**中位数**；
- 近黑帧（母版整帧均亮度 < 8）**剔除并单独计数**；
- 一并报 p25 / p75。

```bash
python eval/runner.py --case-set all   # 出 metrics.jsonl + table.md + badcases.md
```

跨 run 比较时校验口径：`metric_profile` 指纹（现为 `median_v2_blackskipped`），
口径不同会明确提示「两轮 pass/fail 不可直接比较」。

### 2.2 教训二：结论整条作废（16 组配置 → 全部落进同一区间）

口径修正后重跑参数扫描，**16 组配置全部落在 15.6–16.1 dB**，
「余量 ≥12 行就稳」「启发式 vs oracle 差 0.9 dB」等旧结论**全部是近黑帧造出来的假规律**。
→ 「mask 边界放哪、余量给多少」**根本不是杠杆**。

这条反转直接催生了下一章的对照实验：**该优化什么，得先问成一道可测的题**。

### 2.3 教训三：评测必须跑在内存里（编码损失不是「误伤」）

落盘评测时 mp4v 重编码把**区外 PSNR 从 49.1 dB 打到 19.6 dB**——看着像大面积误伤，
其实是编码损失。于是：评测一律在内存中完成；真要落盘用 FFV1（但 580 MB/clip，代价不可接受 → 不落盘）。

### 2.4 教训四：字形像素级 PSNR（字幕区 93% 是干净背景，会稀释误差）

字幕区里 93% 是不该动的背景，在整块区域算 PSNR 会稀释字形上的误差。
于是加了 `eval/metrics.py::psnr_mask`：**只在被字幕字形覆盖的像素上算**。
在选型对照里，这个口径把「引擎差别」和「mask 差别」分开了（§4）。

## 3. 标准层：`spec/` 七份规格

每个环节一份 YAML，五段式固定：

```
input / output（契约 + 不变量）
metric（主指标 + 副指标 + 阈值 + 阈值来源）
degrade_allowed（允许的降级路径 + must_log + forbidden）
budget（超时 / 重试 / 显存 / 成本上限）
cases（必须跑通的 case id）
```

**阈值来源只有四种**，写进 YAML 里，不许含糊：

| 来源 | 含义 | 例子 |
|---|---|---|
| 人眼标定 | 业务方肉眼判定反推 | 人评打分管线 → `thresholds.json` |
| 实测 | 我们跑出来的数 | 翻译成本 $0.00596719/千段 |
| 硬契约 | 不允许违反 | 翻译层「输出段数 == 输入段数」 |
| 初版 | 还没标定 | `threshold_source: C-初版值` |

例子（`spec/translate.yaml`）：

```yaml
- name: 单次请求成本（美元/千段）
  threshold: 0.02
  threshold_source: B-实测（2026-11-25，4 次真实 DeepSeek 调用 32 段）
    实测 $0.00596719/千段（2026-11-25 20:24 快照）；阈值取 3 倍余量。口径：eval/cost.py --scan results/scenarios
```

> 纪律的价值：面试时任何人都可以指着 YAML 问「这个阈值哪来的」，我们有确定答案。

## 4. 选型：用对照实验把「该优化什么」问成一道可测的题

### 4.1 实验设计：一次只动一个变量

`scripts/erase_compare.py` —— 2×2 + 一个负控：

```
修补引擎 {OpenCV 边缘扩散, LaMa 内容感知 ONNX}
   ×  mask 粒度 {全宽横带, 逐文字像素(oracle)}
   +  引擎健全性负控（scripts/engine_sanity.py：在干净母版上挖大洞，不涉及字幕）
```

### 4.2 结果（修正后的 M1_04 / M1_01）

| case | 引擎 / mask | 字幕区 PSNR | SSIM | 字形 PSNR |
|---|---|---|---|---|
| M1_04 | opencv / 横带 | 16.10 | 0.402 | 16.33 |
| M1_04 | lama / 横带 | 17.65 | 0.557 | 16.97 |
| M1_04 | opencv / 逐文字 | 22.88 | 0.819 | 18.12 |
| M1_04 | lama / 逐文字 | **22.68** | **0.828** | 17.94 |
| M1_01 | opencv / 横带 | 18.13 | 0.779 | 16.33 |
| M1_01 | lama / 横带 | 17.79 | 0.836 | 16.92 |
| M1_01 | opencv / 逐文字 | 22.54 | 0.924 | 17.73 |
| M1_01 | lama / 逐文字 | **24.66** | **0.930** | 19.92 |
| — | 基线（不擦除） | — | — | M1_04 5.90 · M1_01 5.50 |

**结论**：mask 粒度 **+6.6 dB**（两条 case 一致）· 引擎 **0~+2 dB**（但 LaMa 的 SSIM 稳定更高）。
→ 优先级：**先做逐文字 mask，再选引擎**。最优组合 LaMa + 逐文字 mask。

### 4.3 这条结论**经历过一次反转**（关键，见 §12 R4）

第一次跑出来，「LaMa + 逐文字 mask」只有 10.46 dB（比 OpenCV 差 8 dB），
我当时的判断是「LaMa 是大洞模型，不支持细笔画」→ **写进了结论**。

后来发现：**那个数恰好等于「什么都不做」的基线**（Δ=0.00）——一个模型不可能精确等于基线，
这更像「模型根本没跑」。绕开自己的封装，把 512×512 tile 直接喂给 ONNX → 模型改了 **90.91%** 的像素。
→ **模型没问题，是我们的封装有问题**：512 高的窗口按 mask 的 `ys.min()/ys.max()` 定位，
而 oracle mask 混入了重编码噪点 → 窗口落在 rows 289–801，**真正的字幕行（~940–1010）在窗口外**
→ 每个瓦片里都没有洞 → 模型原样返回。

修法：`pipeline/inpaint/lama_onnx.py::_row_runs()` 按 mask 的**连续行段**合并成文本行组再开窗口
（多行字幕 → 多窗口），噪点组按像素数剔除；oracle mask 加连通域面积过滤。
→ mask 内被修改像素 **0% → 99.7%**；同一格 **10.46 → 22.68 dB**。

> **留下的纪律**：「模型不支持 X」这种结论，必须先用一个**不经过自己封装**的最小实验去证伪。
> 指标异常到「恰好等于基线」这种程度时，先怀疑自己。

### 4.4 口径纪律的第二个推论：单 case 的引擎结论不可靠

引擎健全性负控（在**干净母版**上挖 256×128 的洞，不涉及字幕）：

| case | OpenCV Δ | LaMa Δ |
|---|---|---|
| M1_01 | — | +4.09 dB |
| M1_02 | — | +3.33 dB |
| M3_01 | — | +2.52 dB |
| M1_04 | — | ≈ 0（该区明亮且失焦） |

→ LaMa 在**大洞**上确实更强，但**单条 case 的结论不可外推**（M1_04 就是反例）。
这条纪律后来也用于约束所有选型结论。

### 4.5 当前状态（诚实版）

`results/2026-11-25_erase_v2`（8/8 通过硬约束，8 条 WARN）：

| case | 字幕区 PSNR | 基线 | Δ | SSIM | 区外 Δ |
|---|---|---|---|---|---|
| M1_01 bottom | 16.53 | 10.37 | +6.16 | 0.770 | 0.0 |
| M1_01 face | 17.10 | 8.00 | +9.10 | 0.648 | 0.0 |
| M1_02 bottom | 21.85 | 7.26 | +14.60 | 0.773 | 0.0 |
| M1_02 face | 21.40 | 7.47 | +13.93 | 0.663 | 0.0 |
| M1_04 bottom | 16.08 | 10.66 | +5.42 | 0.403 | 0.0 |
| M1_04 face | 17.11 | 8.14 | +8.97 | 0.459 | 0.0 |
| M3_01 bottom | 18.81 | 8.76 | +10.06 | 0.807 | 0.0 |
| M3_01 face | 22.74 | 7.74 | +15.01 | 0.810 | 0.0 |

**为什么全部 WARN**：硬约束（区外不误伤 / untouched ≥ 60 dB）全过，
但**调优档**（A 档 25 dB / SSIM 0.75）没达到。原因已定位（不是算法不行）：
**底部字幕的 mask 太宽**——检测出的横带占画面高度 20.7%，而字幕实际只在底部约 60 px，
多擦的 150 px 是真实画面，inpaint 出来是拉伸涂抹。
同样的算法用 **oracle 完美遮罩**能到 **29.96 dB**（≈ 差 13~15 dB）。

→ **下一个杠杆已明确：把 mask 收到文字实际所在的几行**（在已检出的横带内再做行密度剖面，
和面部字幕检测器同一套技术）。初步实验（`scripts/mask_tighten_eval.py`，**在途、未定稿**）
显示收紧并非免费：面积确实从 ~21% 降到 ~15%（recall 0.93~0.99），但字幕区 PSNR
**M1_01 微涨（16.84 → 17.08）、M1_02 反而大掉（21.89 → 16.65）、M1_04 / M3_01 小掉**
→ 一次性收紧不是答案，要的是**跨帧的行稳定性**（多帧投票出共识行带），
而不是每帧各自收紧。这个方向**尚未验证**，写在这里是待办不是结论。

## 5. 端到端跑通

### 5.1 流水线

```
母版/派生件
  → 字幕擦除（subtitle_erase，人脸字幕走 YuNet 检测器）
  → ASR（faster-whisper small int8，CPU，VAD）
  → 翻译（DeepSeek / 任意 OpenAI 兼容端点 / 离线三级降级）
  → TTS（edge-tts）
  → 时间轴回贴 + 变速对齐（atempo，限幅 [0.8, 1.25]）
  → 音轨替换（mux）+ 烧字幕（ASS）
```

**时间轴回贴 + 变速对齐**借鉴 B站开源 `bilibili/Index-Translate` 的 `video-dub/` 骨架（Apache-2.0，注明出处），
但其 S2ST 模型 2B bf16 约 10 GB 显存、本机 8GB 装不下 → 我们用「ASR + 翻译 + 独立 TTS」替代。

### 5.2 四个场景的真实运行（`results/scenarios/*/run.json`）

| 场景 | 方向 | 段数 | ASR | 翻译 | TTS | 擦除 | 降级 | token |
|---|---|---|---|---|---|---|---|---|
| S1_02 | 中→英 | 13 | 4.5 s | 1.6 s | 41.7 s | 42.7 s | 否 | 430 |
| S1_03 | 中→英 | 3 | 3.0 s | 0.9 s | 18.5 s | 42.3 s | 否 | 155 |
| S2_01 | 英→中 | 5 | 3.4 s | 1.0 s | 14.6 s | 91.0 s | 否 | 252 |
| S2_03 | 英→中 | 5 | 2.2 s | 1.5 s | 10.9 s | 38.9 s | 否 | 300 |

- ASR 实时率 **RTF ≈ 0.113**（40 s 音频 4.5 s 出结果，CPU int8）
- 翻译是**全链路最快的环节**（1~1.6 s 处理 13 段）
- 擦除最慢（OpenCV inpaint 逐帧，~130–950 ms/帧，跨 480p/720p/1080p 素材）→ **下一处该优化的就是它**
- 变速统计：S1_02 13 段全部需要拉伸，9 段超长，**最大需要 4.25 倍变速**，
  而我们限幅在 [0.8, 1.25] → 说明**译文偏长**，这是断句/长度对齐要解决的下一个问题

### 5.3 一个诚实的观察：ASR 文本带繁体与港式用词

S1_02 的识别结果如「正陽門外小女人也獲得了五項提名」「都聽好在表演內講像方面收穫破風」——
繁体 + 港式表达。翻译层能处理，但**字幕风格与目标地区（内地）不一致**，
需要在 ASR 后加一道「简繁/用词归一」或换 ASR 解码参数。这条**记为待办，未做**。

## 6. 抗压与降级

### 6.1 故障注入矩阵（`scripts/fault_test.py`，7/7 PASS）

| 注入 | 结果 | 降级行为 |
|---|---|---|
| DNS 解析失败 | PASS | 切离线后端，`degraded=true`，3/3 段仍产出 |
| HTTP 401 | PASS | 同上 |
| HTTP 429 | PASS | 同上 |
| HTTP 5xx | PASS | 同上 |
| 运行中断网 | PASS | 同上 |
| TTS 断网 | PASS | 保留原声，`degraded=true`，写明原因 |
| 媒体文件损坏 | PASS | `ffmpeg -i` 兜底解析；失败则报「容器损坏或无有效流」 |

**判据不是「没崩」，是「按 spec 降级 + 留痕 + 可续跑」**。
`spec/_fault.yaml` 写死了每个环节允许的降级路径与 `forbidden`（禁止静默失败、
禁止静默把原文当译文而不标 degraded）。

### 6.2 失败四分类（`docs/notes/09-抗压与失败归类.md`）

```
模型不行 / 素材不可解 / 环境限制 / 我们的代码有 bug ← 第四类是自己的责任
```

**我们自己挖出来的 5 个 bug**（都属于第四类）：
① 检测器只取 argmax 带 ② 均值 + 近黑帧 ③ LaMa 后处理多乘 255
④ 512 窗口被噪点带偏 ⑤ 评测落盘混进编码损失。

> 第四类值得单独说：**它是这个项目里最值钱的部分**。
> 因为「模型不行 / 素材不行」是外部问题，而「我们的代码有 bug」是**我们能改**的——
> 而且只有把失败归因做成流水线的一部分，错误才会在交付前被拦下，而不是交付后被用户发现。

## 7. 接入层：把外部 API 接进公司网关

`pipeline/gateway/` —— 五个职责，都实现了、都在本地 mock 上验证过：

| 职责 | 实现 | 关键决策 |
|---|---|---|
| 凭据治理 | `client.py::GatewayConfig` | 只从环境变量/`.env` 读；日志只留 `sha256[:8]` 指纹 |
| 模型白名单 | 请求发出**前**本地拦 | 白名单外的模型 0 ms 被拒，不发出去 |
| 限流 | `_RateLimiter` | 客户端侧 RPM 排队，不把 429 打给上游 |
| 重试退避 | `_post()` | 401/403/参数错 → **不重试**；429 → 尊重 `Retry-After`；5xx → 指数退避 |
| 熔断 | `_Breaker` | 熔「打不通」，**不熔「让你慢」** |
| 审计 | `audit.py` | 请求/响应体**默认不落盘**；只记谁、何时、哪个模型、多少 token、耗时 |

实测（`scripts/gateway_demo.py` + `scripts/mock_gateway.py`）：

| 场景 | 行为 | 耗时 |
|---|---|---|
| 正常 | OK | 38 ms |
| 模型不在白名单 | 本地拦截 | **0 ms**（根本没发出去） |
| token 不对 | 不重试，直接报鉴权失败 | 153 ms |
| 连续 5 次 / rpm=3 | 3 OK → 1×429 → OK | 429 那次等 **58.9 s**（尊重 Retry-After） |

**熔断语义的设计修正**（我自己踩的坑）：第一版把 429 也计进熔断失败次数，
一次限流就打挂了后续调用（14 ms 内直接失败）→ 改为 **429 只退避不熔断**；
重测：3 OK → 429 → OK，熔断器保持闭合。

**与翻译层的关系**：网关不是另起一套，而是在 provider 之上包一层——
主后端失败 → 网关重试/退避/熔断 → 仍失败切下一后端 → 最后落离线降级并留痕。
凭据从不在代码里，也永不明文进日志。

> ⚠️ 边界：这是**本地 mock 网关**验证的，**没有接公司真实网关**（鉴权协议 / 白名单规则 / 审计字段要求未知）。

## 8. 成本：口径、账单、以及「钱到底花在哪」

### 8.1 口径的唯一来源：`pipeline/pricing.py`

单位：美元/百万 tokens；**高峰时段单价 ×2**（UTC 周一至周五 01–04 / 06–10 = 本地工作日 09–12 点、14–18 点）。

| 模型 | 输入（缓存命中） | 输入（未命中） | 输出 |
|---|---|---|---|
| `deepseek-flash` | $0.003 | $0.15 | $0.60 |
| `deepseek-v4-pro` | $0.022 | $0.66 | $1.98 |

来源：官方定价页（2026-11-25 抓取核实，非记忆）。
旧模型名 `deepseek-chat` 按官方说明折算到 flash 价（**实测旧名 11-25 仍可调用**）。

### 8.2 账单（`python eval/cost.py --scan results/scenarios`）

| 环节 | 本项目实际 | 反事实（换成 DeepSeek 官方托管 API，list price） |
|---|---|---|
| 翻译 | **$0.00019** / 1.98 分钟音频 | 同上 |
| ASR | **$0**（本地 faster-whisper） | $0.00382 |
| TTS | **$0**（edge-tts） | $0.05031 |
| **合计** | **$0.00019** | **$0.05413**（≈ **283×**） |

### 8.3 这条结论改变了做法

（快照 2026-11-25 20:24：4 次运行 / 32 段 / 1.98 分钟音频；**总数会漂**，费率
`$0.0000966/分钟音频`、`$0.0060/千段` 才是稳定口径）

一开始我以为「省 API 账单」= 优化翻译 Prompt / 缩短上下文。算完发现**翻译只占账单的 0.4%**，
**大头是 ASR + TTS（99.6%）**。所以真正该做的降本是：ASR/TTS 不托管化（我们已经是）、
缓存复用、模型分级路由、批量作业排非高峰（零成本，直接对折）。
**「优化翻译 Prompt 省 API 账单」是个看起来对、实际没用的结论。**

账单还单列了 `degraded_cost_usd` 与 `retried_calls`——**重试和降级花掉的钱不会因为
「最后成功降级」而消失**，这两列就是「效果不达标却已经花掉的钱」。

口径纪律：token 拆分精确的行与只有总数的行分别标注；口径不同的两轮账单**不可直接比**。

## 9. 人评闭环：判定权留给人

`eval/human_review/` —— 三段链路：

```
① 出题    make_items.py    → 成片 mp4 + 自动指标 + 成本，8 条待评条目
② 人打分  reviews.json     → erase/break/lip/style/sub/overall（1–5 分，5=最好）
③ 反推    build_packet.py summarize → 阈值候选 + 达标成本 + badcase 清单
```

`summarize` 的输出就是下一轮要改的东西：

| 输出 | 含义 | 怎么用 |
|---|---|---|
| `metric_thresholds[].candidate` | 阈值候选 | 写回 `spec/*.yaml`，注明**来源=人评** |
| `metric_thresholds[].separable` | 这个指标能不能分开好坏 | 不能分开的指标就该从验收标准里删掉 |
| `cost.good_usd` | 达标样本花了多少 | 降本的**上限目标** |
| `cost.bad_usd` | 不达标样本花了多少 | 该砍掉的预算 |
| `bad_samples` | 人判不可接受的样本 | 拉进 badcase 清单做归因 |

**设计上的关键点**：自动指标**只作为参考列**，不作为判定权。
`NON_QUALITY_METRICS` 明确排除 `psnr_baseline` / `psnr_delta` / `untouched_out_mask`
（前者是素材自带的编码损失，与成片好坏无关；后者是硬约束不是可调档位）。

> ⚠️ 当前 `results/human_review/reviews.json` **仍是空的**（等人打分）。
> `reviews.simulated.json` 是按指标自动填的**模拟打分**，只用来证明链路通，
> 文件里带 `_simulated` 标记，**不能当结论引用**。

## 11. 能力边界声明（明确不做什么，以及为什么）

**口型同步：不做。** 这是有依据的工程判断，不是能力缺失：

## 13. 素材版权与合规红线

- 母版全部来自 **Wikimedia Commons**，许可与 SHA256 登记在 `assets/manifest.json`；
- **不使用 B站原片作为素材**；BLG 相关只登记 URL + BV 号 + SHA256 + 用途，文件不入库、不传播、不二次分发；
- 仓库只留 manifest / meta / cases，母版与派生件按 SHA256 **确定性重建**；
- `edge-tts` 与 `faster-whisper` 均为本地/免费栈，不产生内容外传；
- 调 DeepSeek 的只有**字幕文本**（不含音频、不含画面）。

## 15. 一句话总结

> 我做的不是一个译制 demo，而是一套**能让译制流水线的产出敢交付**的评测与验收系统：
> 有单一口径的指标、有注明来源的阈值、有 7/7 通过的降级矩阵、有不落凭据的网关审计、
> 有可复跑的成本账单、有人评反推阈值的闭环，以及一份**把错的结论也留着**的迭代记录。
> 它的价值不在于「跑通了」，在于**每一条结论都能被追问到一条命令**。
