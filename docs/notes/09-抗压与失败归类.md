# 抗压与失败归类

> 对应 JD 职责「保障线上任务的稳定性与持续运行」，以及用户提的
> 「测试如果服务器突然断网，这套 Pipeline 会不会直接挂掉」。
>
> 本文只写**跑过并留痕**的结论；没做的明确写「未做」。

---

## 0. 一句话结论

**断网不会让 Pipeline 挂掉，但会降级；降级必须留痕。**
7 条故障注入用例全部 PASS：进程不崩、每个降级都带 `degraded=true` + 可读原因、
翻译自动落离线后端、TTS 全网不通时保留原声继续出片、坏素材只影响单个 case。

但**稳定性不等于质量**：降级成片是「能交付的降级版本」，不是「合格的译制片」。
所以降级必须同时打上 `degraded` 标记并进入 badcase 清单，不能静默通过。

## 1. 故障注入矩阵（`scripts/fault_test.py`，证据 `results/2026-11-25_fault/faults.json`）

| 用例 | 注入 | 结果 | 观测到的降级行为 |
|---|---|---|---|
| translate/dns_fail | 域名解析失败 | PASS | 最终后端=offline，degraded=True，段数 3/3，失败尝试 1 次，~1.5s |
| translate/http_401 | 鉴权失败 | PASS | 同上。**401 不重试**（重试无意义，直接切下一后端） |
| translate/http_429 | 限流 | PASS | 同上；429 按 spec 退避后再切后端 |
| translate/http_5xx | 服务端错误 | PASS | 同上 |
| translate/network_gone | 端点指向不可达地址（真实 socket 失败） | PASS | 同上 |
| tts/network_gone | 全部 TTS 后端抛异常 | PASS | degraded=True，段数 0，原因「所有 TTS 后端均失败，保留原声」 |
| media/corrupt | 伪造的坏 mp4 | PASS | probe 不抛异常，返回 `source=ffmpeg_stderr` + error 文案 |

**7/7 通过。** 复现：

```bash
python scripts/fault_test.py --json results/2026-11-25_fault/faults.json
```

### 三条设计原则（对应 `spec/_fault.yaml`）

1. **任何外部依赖失败都有明确下一步**，不抛异常终止 —— 翻译链是
   `deepseek → openai_compatible → offline`，TTS 链末尾是「保留原声」。
2. **降级必须留痕**：`stat.degraded=true` + `stat.error` + `stat.extra.attempts`
   （失败尝试次数），禁止静默降级。
3. **失败的钱也要算**：超时/重试的调用照样计费 →
   `eval/cost.py` 的 `degraded_cost_usd` 单独统计这一块。

### 断网时的最终形态

```
翻译层全挂 → 术语表离线翻译（内容是模板化的，但句子数、时间轴对得上）
TTS  全挂 → 保留原声
       ↓
仍然产出一条「降级成片」+ 一份降级报告（每段标 degraded 与原因）
```

**这就是「兜底」的准确含义**：不是「不出错」，而是「出错时仍交付一个标注清楚的版本」。

## 2. 失败归因：四类，处理方式完全不同

这是本项目最该沉淀的一条经验：**失败不是同一种东西，混在一起就没法优化。**

| 类别 | 定义 | 处理方式 | 本项目实例 |
|---|---|---|---|
| **① 模型不行** | 模型能力/适用域不足 | 换模型、换方案、接受降级 | LaMa 是「大洞模型」；细笔画 mask 上表现不如边缘扩散（见文档 10 §3） |
| **② 素材不可解** | 输入本身缺信息 | 标 badcase，排除出评测集 | M1_04 是高光/失焦画面，SSIM 结构上不可能高 |
| **③ 环境限制** | 硬件/网络/依赖缺失 | 降级、留痕、给替代路径 | 无 GPU → torch CPU 版；ffprobe 缺失 → `ffmpeg -i` 兜底解析 |
| **④ 我们的代码有 bug** | 实现错误 | **自己修**，写进注释与文档 | 见 §3，五个实例 |

**④ 是我们自己的责任，不能推给模型，也不能推给素材。**

## 3. 我们自己的五个 bug（这一节是本文的重点）

这五个都是**指标先给了异常信号，然后定位到根因**的实例。写进报告比藏起来值钱。

### 3.1 检测器只取 argmax 带 → 双行字幕残留半屏

- **现象**：字幕区 PSNR 只有 10.9dB，肉眼看字幕擦了一半。
- **根因**：边缘密度检测只取「最高的一条横带」，双行字幕的第二行没被覆盖。
- **修法**：改成「取包含峰值带的**连续合格段**」→ 同一条 case 指标翻倍。
- **教训**：检测逻辑一行改动的能量，和换模型一个量级 —— **先查自己的代码。**

### 3.2 指标用均值 + 近黑帧 → 结论反复横跳

- **现象**：同一条 case、同一份素材，采样帧数 4/6/8/12 时 PSNR 分别是
  16.07 / 29.89 / 26.46 / 16.09 dB。
- **根因**：素材含**近黑帧**（母版整帧均亮度≈0），黑帧上擦完还是黑 →
  与母版逐像素相同 → **PSNR 恒 99dB**，把均值拉飞。
- **修法**：主指标改**中位数** + 近黑帧剔除并单独计数 + 报 p25/p75。
- **教训**：**指标口径错了，结论会反过来** —— 旧口径下「余量给够就能过 30dB」
  的结论，换口径后整条作废（16 组配置全部落在 15.6–16.1dB）。

### 3.3 LaMa ONNX 后处理多乘了一次 255

- **现象**：模型输出「一块白斑」，一度以为是模型在大洞上失败。
- **根因**：那个 ONNX 图的输出**已经是 0–255**，我们又乘了一次 255 → 全图饱和。
- **判定方法（不靠猜）**：拿**非洞区**跟输入逐像素比 —— 正确的后处理下应当完全一致（PSNR=99）。
- **修法**：`_post` 只做 clip 不做缩放；判定方法写进了 `pipeline/inpaint/lama_onnx.py` 的 docstring。

### 3.4 LaMa 512 窗口定位被噪点带偏 → 模型什么都没补

- **现象**：M1_01 上「LaMa + 逐文字 mask」的输出与输入**逐像素相同**（0 个像素被改），
  指标上等于「什么都不做」的基线。
- **第一层误判**：「LaMa 不支持细笔画 mask」（写成结论了）。
- **挖到底**：直接测模型 —— 同一个模型、同样的细笔画 mask，**能改 90% 的像素**，
  说明模型没问题，是**我们的分块逻辑**有问题。
- **根因**：512 高的纵向窗口按 mask 的 `ys.min()/ys.max()` 定位，而 oracle mask 里混进了
  **重编码噪点**（母版与派生件在全画面都有微小差异）→ 窗口算出来落在 rows 289–801，
  **真正的字幕行（~940–1010）在窗口外** → 每个瓦片里都没有洞 → 模型原样返回。
- **修法**（两处）：① `LamaOnnx._row_runs()`：按 mask 的**连续行段**开窗口（多行字幕 → 多窗口），
  忽略噪点段；② oracle mask 加**连通域面积过滤**，只留字形笔画，丢掉孤立噪点。
- **修完**：mask 内被修改像素 0% → **99.8%**。
- **教训**：**指标异常时先怀疑自己的代码**。「模型不支持 X」这种结论，
  必须先用一个不经过自己封装路径的最小实验去证伪。

### 3.5 评测落盘把编码损失混进修补质量

- **现象**：区外 PSNR 只有 19.6dB，看起来像「擦除误伤了画面」。
- **根因**：落盘用 mp4v 又编了一次；**第二次有损编码**把整帧拉垮。
- **修法**：评测一律**编码前**（`eval/metrics.py::subtitle_erase_in_memory`），
  且任何绝对指标都**成对报 baseline**。
- **附带发现**：无损 FFV1/MKV 一条 25s 720p 要 580MB → 评测**不落盘**。

## 4. 还没做的（诚实缺口）

| 项 | 状态 | 为什么 |
|---|---|---|
| **真·断网整条链路**（拔网线跑整条 pipeline） | 🟡 部分做 | 注入的是**环节级**故障（翻译/TTS/媒体探测），不是物理断网；整链路断网还需在真机环境验一次 |
| **长片（30min+）抗压** | 🟡 由场景素材覆盖 | 场景素材 S1_02/S1_03/S2_0x 是真实片源（含真烧录字幕、真方言、真外语片），clip 30–70s；**整段长片尚未跑通** |
| **熔断器真实触发** | 🔶 未验 | `spec/_fault.yaml` 写了「连续 429 → 熔断 60s」，但注入用例没覆盖熔断状态机本身 |
| **断点续跑** | 🟡 部分做 | 每阶段产物落盘 + 幂等键已实现；「中断后从第 N 段续跑」未做端到端验证 |
| **磁盘满（errno 28）** | 🔶 未注入 | spec 有策略，无用例 |
| **GPU 路径** | ❌ 本机不具备 | torch 是 CPU 版；超分走 ncnn-vulkan 路线，口型只做 ONNX CPU |

## 5. 复现命令

```bash
cd video-dubbing-pipeline
python scripts/fault_test.py --json results/2026-11-25_fault/faults.json   # 7/7
python scripts/audit_assets.py                                            # 素材自检
python scripts/probe_media.py --file <素材>                                # 坏元数据探测
```

**口径纪律**：故障注入的「通过」= 进程不崩 + `degraded=true` + 有可读原因 +
产出条数符合预期；**不把降级当成成功交付**（降级成片单独标注，不计入合格线）。
