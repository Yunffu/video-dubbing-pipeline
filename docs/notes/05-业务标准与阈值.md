# 业务标准与阈值：谁定、怎么定、怎么校准

> 对应 JD 职责 2「效果测试和方案对比」、职责 3「评估效果、耗时、成本及稳定性」。
> 这份文档解释 `spec/*.yaml` 背后的**方法**，不是把 YAML 再抄一遍。

---

## 1. 为什么标准要单独一层

如果只写代码，交付物是「一条能跑通的流水线」，它的质量只能靠肉眼看片。
业务上真正要的是另一件事：**换一个方案之后，怎么知道是变好还是变坏**。

所以标准层（`spec/`）的定位是：

| 层 | 谁写 | 产出 | 出问题谁负责 |
|---|---|---|---|
| 第 4 层 实现 | agent（照 spec 写） | pipeline 代码 | 实现的人 |
| **第 5 层 约束与验收** | **人定阈值，agent 维护** | **spec + runner + badcase 清单** | **定阈值的人** |

这正是「agent 能写 Demo，但不敢上线」缺的那一层。

---

## 2. 每个 spec 的五段（缺一段就不算可执行）

```yaml
input / output        数据契约（字段、不变量）
metric / threshold    主指标 + 副指标 + PASS 阈值 + 阈值来源
degrade_allowed       允许的降级路径（每条都要 must_log）
budget                耗时 / 显存 / 成本上限
cases                 必须跑通的 case id
```

`threshold_source` 字段是刻意设计的：**阈值的来源必须能被追问**。我们目前的来源分三类：

| 来源 | 含义 | 例子 | 现状 |
|---|---|---|---|
| 人眼标定 | 「超过这个数我一眼能看出来不行」 | 唇音偏移 > 80ms、字幕区 PSNR < 30dB | **待用户拍板** |
| JD 职责 | 从 JD 原文推出的硬性要求 | 失败率 ≤5%、必须评估耗时/成本/稳定性 | 已定（C 级） |
| 上游硬约束 | 受环境/物理限制倒逼 | RTF ≤1.0、变速幅度 ≤25% | 已定（C 级） |

## 3. 当前阈值状态：哪些能判、哪些不能判

| 环节 | 主指标 | 阈值 | 状态 | 谁能定 |
|---|---|---|---|---|
| ASR | CER | ≤0.08 | 初版（C 级） | 人眼标定 + 数据校准 |
| 翻译 | 段级时长偏差 Δt | ≤0.5s | 初版（C 级） | 人眼标定 |
| 翻译 | 漏解析段数 | =0 | **硬契约**（已定） | — |
| TTS | 尾部静音 | ≤0.3s | 初版（C 级） | 人眼标定 |
| TTS | 音色一致性 | 人工 | 人工指标 | 用户 |
| 字幕擦除 | 字幕区 PSNR | ≥30dB | 初版（C 级） | 人眼标定 |
| 字幕擦除 | 区外 PSNR | 不低于原片 | **硬约束**（已定） | — |
| 口型 | 唇音同步偏移 | ≤80ms | 初版（C 级） | 人眼标定 |
| 口型 | 帧率粒度 | 25fps → 40ms/帧 | **物理上限**（已定） | — |
| 合成 | 时长偏差 \|ΔT\| | ≤0.5s | 初版（C 级） | 人眼标定 |
| 合成 | overshoot 段数 | =0 | **硬约束**（已定） | — |
| 端到端 | 失败率 | ≤5% | 初版（C 级） | 批量跑分校准 |

**诚实的现状**：这些初版值是**我按行业常识填的，不是业务判断**。它们的作用是让跑分器今天就能跑；
真正的定稿要等两件事：
1. **用户看片给出的判定**（哪一版更好、差在哪）；
2. **用跑分数据反向校准**（把「肉眼不行的样本」和「指标最差的样本」对齐，看阈值该定在哪）。

这就是文档里说的「阈值不是拍的，是先人眼标定、再用数据校准」。

## 4. 阈值怎么从「人评」变成「自动判」

人评与自动指标不是二选一，而是**互相校准**：

```
用户看片打分（断句/口型/翻译腔/字幕遮挡）
        ↓ 同一条 case
自动指标（CER / Δt / PSNR / SyncNet offset / overshoot）
        ↓ 找相关性
把「用户判不行」的样本的指标分布画出来 → 阈值取分界处
```

具体到人评工作台（`eval/human_review/`）的设计：
- 每个 case 一行：自动指标 + 用户四项打分（1–5）+ 用户文字意见；
- 每轮复盘把「用户判不行的样本」和「指标异常的样本」对齐；
- 出现「指标好但用户判不行」→ 说明**指标选错了**（这是更贵的教训，要写进报告）。

## 5. 降级与阈值的关系

降级不是「失败」，是**在阈值不满足时换一条可接受的路**，但必须留痕：

| 场景 | 降级动作 | 留痕字段 |
|---|---|---|
| 断网/限流/鉴权失效 | 翻译切离线术语表；TTS 保留原声 | stat.degraded=true、attempts[]、warnings[] |
| 译文长度超出变速上限 | 保留原速 + overshoot 计数 | mix.stats.overshoot |
| 字幕烧录失败 | 只出外挂 .ass/.srt | stat.degraded=true |
| 口型方案不可用 | 保留原画面 | detail 写明显存/License 依据 |

**禁止**：静默失败、静默把原文当译文、把没做的环节报成 PASS。

## 6. 现在该用户拍板的三件事

1. **唇音同步偏移阈值**：超过多少毫秒你一眼能看出来嘴和音对不上？（初版 80ms）
2. **字幕擦除 PSNR 阈值**：多大的修补痕迹你能接受？（初版 30dB）
3. **ASR CER 阈值**：译制场景下，多少比例的错字可以接受进下一环？（初版 8%）

拍板后我把这些写回 `spec/*.yaml` 的 `threshold_source`（标为「人眼标定 YYYY-MM-DD」），
再用已有跑分数据校准，看初版值偏严还是偏松。
