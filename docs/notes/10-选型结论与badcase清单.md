# 选型结论与 badcase 清单（阶段 2 收口）

> 对应 JD 职责 2「效果测试和方案对比」、职责 3「评估效果、耗时、成本及稳定性」。
> 本文只写**有数据支撑**的结论；没跑过的方案一律标「未在本机验证」，不写结论。
> 复现命令见 §7。**所有数字都是「中位数 + 剔除近黑帧」口径**（见 §2）。

---

## 0. 一句话结论

**要优化的是「mask 粒度」，不是「修补引擎」。**

同一张 mask 上换引擎（OpenCV 边缘扩散 → LaMa 内容感知），字幕区 PSNR 只动
**0 ~ +2 dB**；而把 mask 从「全宽横带」换成「逐文字像素」，同样用 OpenCV，
字幕区 PSNR **+6.6 dB**（M1_04：16.10 → 22.88；M1_01：18.13 → 22.54），
SSIM **+0.1 ~ +0.4**。

最优组合是 **LaMa + 逐文字 mask**：M1_01 达到 **24.66 dB / SSIM 0.930**，
M1_04 达到 22.68 dB / SSIM 0.828。

引擎本身不是不能用 —— 独立的大洞重建实验里，LaMa 比 OpenCV 好 **+2.5 ~ +4.1 dB**
（4 条 case / 3 个洞位，见 §4）。**先做 mask，再选引擎**，这个顺序是数据给的。

## 1. 方案 A：OpenCV inpaint（自研基线）现状

### 1.1 实现

- `pipeline/subtitle_erase.py`：检测（横带边缘密度法）+ 修补（`cv2.inpaint`，TELEA/NS）
- `pipeline/face_sub.py`：人脸字幕定位（YuNet ONNX，矩形 mask）
- `scripts/erase_subtitles.py`：单条出片（落盘 mp4v，可选 FFV1/MKV 无损）
- `scripts/erase_sweep.py`：参数扫描（mask 来源 × 余量 × 算法），不落盘
- `scripts/erase_compare.py`：引擎 × mask 粒度 对照实验（本文 §3 的数据源）
- `scripts/engine_sanity.py`：引擎健全性（挖大洞，与字幕无关）—— 本文 §4 的数据源
- 指标：`eval/metrics.py` 的 `subtitle_erase_in_memory()`

### 1.2 检测口径踩过的坑

v1 只取「边缘密度最高的**一条**横带」→ 双行字幕只擦到第二行，**残留半屏字**，
in-mask PSNR 只有 10.9dB。v2 改成「取**包含峰值带的连续合格段**」→ 指标翻倍。
**同一个模型，检测逻辑改一行，指标翻倍。**

### 1.3 跑分结果（`eval/runner.py --stage subtitle_erase --frames 24`）

run_id `2026-11-25_erase_v2`，case 集 = `assets/cases.json` 全部 8 条 hard_sub 类：

| case | 难度 | 字幕区 PSNR | baseline | Δ | SSIM | 区外Δ | 判定 |
|---|---|---|---|---|---|---|---|
| M1_01__hard_sub_bottom | 底部 | 16.53 | 10.37 | +6.16 | 0.770 | 0.0 | WARN |
| M1_01__hard_sub_face | 压脸 | 17.10 | 8.00 | +9.10 | 0.648 | 0.0 | WARN |
| M1_02__hard_sub_bottom | 底部 | 21.85 | 7.26 | +14.60 | 0.773 | 0.0 | WARN |
| M1_02__hard_sub_face | 压脸 | 21.40 | 7.47 | +13.93 | 0.663 | 0.0 | WARN |
| M1_04__hard_sub_bottom | 底部 | 16.08 | 10.66 | +5.42 | 0.403 | 0.0 | WARN |
| M1_04__hard_sub_face | 压脸 | 17.11 | 8.14 | +8.97 | 0.459 | 0.0 | WARN |
| M3_01__hard_sub_bottom | 底部 | 18.81 | 8.76 | +10.06 | 0.807 | 0.0 | WARN |
| M3_01__hard_sub_face | 压脸 | 22.74 | 7.74 | +15.01 | 0.810 | 0.0 | WARN |

- **硬约束全过（8/8）**：区外 Δ **恒为 0.0**、mask 外像素 PSNR = 99dB

> 已被近黑帧污染）。**以本表为准**，见 §2。

## 2. 指标口径：这个坑比算法本身值钱

### 2.1 坑一：PSNR 必须带 baseline 对照

派生件 = 母版 + 烧字幕 + libx264 重编码，所以「派生件 vs 母版」本身就有编码损失。
不报 baseline 直接看绝对值，会把编码损失误判成擦除失败。

### 2.2 坑二：主指标必须用**中位数**，且近黑帧要剔除

v1 用「采样帧均值」。同一条 case M1_04 换采样帧数：

| 采样帧数 | 4 | 6 | 8 | 12 |
|---|---|---|---|---|
| v1 均值 PSNR | 16.07 | 29.89 | 26.46 | 16.09 |

**同一份素材，指标在 16–30 dB 之间乱跳。** 根因：素材里有**近黑帧**
（母版整帧均亮度 ≈ 0），黑帧上「擦除」= 擦完还是纯黑 → 与母版逐像素相同
→ **PSNR 恒 99dB**。采到黑帧就把均值拉飞。

修正（v2 口径，已落到代码）：① 近黑帧（母版帧均亮度 < 8）单独计数、不进主指标；
② 主指标用**中位数**；③ 同时报 p25/p75/样本数。
`eval/metrics.py` 的 `metric_profile = median_v2_blackskipped` 就是这个口径的指纹，
`eval/runner.py` 还会检查两轮口径是否一致（口径不同 → pass/fail 不可直接比）。

### 2.3 坑三：口径一换，**结论会反过来**

同一份 `erase_sweep.py` 参数扫描（16 组配置），换口径前后：

| 结论 | 均值口径（v1） | 中位数口径（v2，24 帧） |
|---|---|---|
| 「mask 边界落在字上会崩」 | oracle margin=0/4 → 18.7 / 20.1 dB | 全部配置 **15.6–16.1 dB**，无差别 |
| 「余量 ≥12 行就稳」 | margin≥12 → **29.5–30 dB** | margin 4 → 16.11、12 → 16.14、24 → 15.96、40 → 15.62 |
| 「启发式 vs oracle 差很多」 | 差 0.9 dB | 差 **0.03 dB** |

**旧结论整条作废**：全宽横带 inpaint 的字幕区 PSNR 稳定在 ~16 dB，
**mask 边界放在哪、余量给多少都救不回来**（差值 < 0.5 dB）。
真正有效的是**换成逐文字像素 mask**（§3，22.9 dB）。

> 这就是「口径纪律」的活例子：**指标口径错了，结论会反过来**，
> 而且错的方向是让人以为「再调调参数就能过阈值」—— 会浪费整个方案周期。

## 3. 变量隔离实验：引擎 × mask 粒度（`scripts/erase_compare.py`）

设计：**一次只动一个变量**。引擎 {OpenCV 边缘扩散, LaMa 内容感知} ×
mask {全宽横带（启发式检出）, 逐文字像素（GT oracle）}，外加一格健全性对照。
oracle mask = 用 GT 差分算出「字幕字形的真实像素」，**只在评测里可用**（生产没有 GT），
它代表「如果检测器足够准，最好能到多少」。

M1_04，8 帧，中位数口径：

| 配置 | 字幕区 PSNR | SSIM | **字形像素 PSNR** | Δ字形 | 区外 PSNR |
|---|---|---|---|---|---|
| （基线）不擦除 | — | — | 5.90 | 0.00 | — |
| opencv / 全宽横带 | 16.10 | 0.402 | 16.33 | +10.44 | 42.52 |
| **lama / 全宽横带** | **17.65** | **0.557** | **16.97** | **+11.08** | 42.52 |
| **opencv / 逐文字像素(oracle)** | **22.88** | **0.819** | **18.12** | **+12.24** | 42.18 |
| **lama / 逐文字像素(oracle)** | 22.68 | **0.828** | 17.94 | +12.06 | 42.34 |

M1_01，4 帧，中位数口径（复现同一结论）：

| 配置 | 字幕区 PSNR | SSIM | 字形像素 PSNR | Δ字形 | 区外 PSNR |
|---|---|---|---|---|---|
| （基线）不擦除 | — | — | 5.50 | 0.00 | — |
| opencv / 全宽横带 | 18.13 | 0.779 | 16.33 | +10.83 | 43.02 |
| lama / 全宽横带 | 17.79 | **0.836** | **16.92** | +11.42 | 43.02 |
| opencv / 逐文字像素(oracle) | 22.54 | 0.924 | 17.73 | +12.23 | 40.98 |
| **lama / 逐文字像素(oracle)** | **24.66** | **0.930** | **19.92** | **+14.42** | 42.59 |

新增口径 **字形像素 PSNR**（`eval/metrics.py::psnr_mask`）：
只在「被字幕盖住的那批像素」上算。理由：字幕区 93% 是干净背景（两边逐像素相同），
它会把字形上的误差稀释掉 —— 同一个引擎换个裁法能差好几 dB，这个指标才是真正要修的东西。

**读出来的三件事**：

1. **mask 粒度是主要矛盾**（两条 case 都是 **+6.6 dB**：16.10 → 22.88、18.13 → 22.54；
   SSIM +0.42 / +0.15）。同样的引擎，只把 mask 从「整带」换成「逐文字像素」就拿到绝大部分收益。
2. **引擎的影响是 0 ~ +2 dB**：逐文字 mask 上，LaMa 在 M1_01 领先 2.12 dB、在 M1_04 打平
   （−0.20）；整带 mask 上，LaMa 在 M1_04 领先 1.55 dB、在 M1_01 打平（−0.34）。
   **换成 LaMa 之前，先把 mask 做对。**
3. **LaMa 在 SSIM 上稳定更好**（0.557 / 0.836 / 0.828 / 0.930 vs OpenCV 的 0.402 / 0.779 / 0.819 / 0.924）。
   生成式补出来的内容比边缘扩散的涂抹**更像真实背景** —— 这正是它该赢的地方，
   而 PSNR 恰好对「补得像但不完全一样」不友好。

> **可迁移的结论**：先做逐文字 mask（+6.6 dB），再选引擎（0~+2 dB，但 SSIM 更稳）。
> 最优组合 = **LaMa + 逐文字 mask**（M1_01：24.66 dB / SSIM 0.930）。
> 下一块拼图是**逐文字检测器**（oracle mask 只在评测里可用，生产要靠 PaddleOCR 之类的检测器）。

> ⚠️ **本节结论经历过一次反转**，值得单独记一笔：
> 第一版实测里「LaMa + 逐文字 mask」只有 10.46 dB（比 OpenCV 差 8 dB），
> 当时判为「LaMa 是大洞模型、不支持细笔画」并写进了结论。
> 挖下去发现是**我们自己的 bug**：512 高的纵向窗口按 mask 的 `ys.min()/ys.max()` 定位，
> 而 oracle mask 里混着重编码噪点 → 窗口落在 rows 289–801，**真正的字幕行在窗口外**
> → 模型什么都没补。修完之后同一格变成 22.68 dB。
> **「模型不支持 X」这种结论，必须先用一个不经过自己封装的最小实验去证伪。**
> 详见 `docs/notes/09-抗压与失败归类.md` §3.4。

## 4. 引擎健全性（与字幕无关的负控，`scripts/engine_sanity.py`）

上面第 3 条说「LaMa 对细笔画差」，得证明不是我们包装错了。
办法：拿**母版**（无字幕）人为挖一个 256×128 的洞，让引擎补，只在洞内跟母版比。

4 条 case × 3 个洞位（上部 / 中部 / 左下），中位数：

| case | OpenCV 洞内 PSNR | LaMa 洞内 PSNR | Δ(lama−opencv) |
|---|---|---|---|
| M1_01 | 16.13 | 20.22 | **+4.09** |
| M1_02 | 23.15 | 26.48 | **+3.33** |
| M1_04 | 16.48 | 16.44 | −0.04 |
| M3_01 | 18.83 | 21.35 | **+2.52** |

**结论**：
- LaMa 在大洞上**确实更强**（3/4 条 case 领先 2.5–4.1 dB）。
- M1_04 是**离群 case**（Δ≈0）：该素材是高光/失焦画面，大洞里没有可推断的结构。
  → **单条 case 得出引擎结论是不可靠的**，这是本项目第二条口径纪律
  （第一条是指标口径，第二条是样本量）。

> 顺带一个踩坑记录：LaMa ONNX 最初输出「一块白斑」，一度以为是模型在大洞上失败，
> 实际是**我们的后处理错了** —— 那个 ONNX 图的输出已经是 0–255，我们又乘了一次 255。
> 判定方法不靠猜：拿**非洞区**跟原图逐像素比，正确的后处理下应当完全一致（PSNR=99）。
> 这条经验已写进 `pipeline/inpaint/lama_onnx.py::_post` 的 docstring。

**为什么 B 值得接**：A 的两个死结（误伤画面、无时序一致性）B 都有对应解法

**我们自己的 LaMa ONNX 已经补上了 B 的「引擎」那一半**（Apache-2.0，208MB，CPU 可跑），
缺的只是 B 的**检测器**（PaddleOCR 逐文字框）。所以下一步不是「引入整个 B」，
而是「用现有检测能力做逐文字框 mask + 按 mask 形状选引擎」。

## 6. badcase 清单与归因

归因四分类（模型 / 素材 / 环境 / 代码）——**这四类处理方式完全不同**：

| case | 现象 | 归因 | 处理 |
|---|---|---|---|
| M1_04__hard_sub_bottom | 16.08dB / SSIM 0.403（最差） | **素材**（高光失焦背景，SSIM 结构上不可能高） | 逐文字 mask；该素材单独标「背景不可靠」 |
| M1_01__hard_sub_bottom | 16.53dB / SSIM 0.770 | **方法论**（全宽带） | 逐文字 mask |
| M1_02__hard_sub_bottom | 21.85dB | **方法论 + 素材** | 同上 |
| M3_01__hard_sub_bottom | 18.81dB / SSIM 0.807 | **方法论** | 同上 |
| 8 条 hard_sub_face | 全部 WARN，无 FAIL | **方案边界**（整带 inpaint 结构不像） | 逐文字 mask；face 侧已有 YuNet 矩形定位 |
| LaMa / 逐文字像素 | 初版 10.46dB（比 OpenCV 差 8dB） | **我们的代码 bug**（512 窗口被噪点带偏 → 模型什么都没补） | 已修；修完 22.68dB，见 §3 的反转记录 |
| M1_04 引擎健全性 | Δ≈0（LaMa 未领先） | **素材**（无可推断结构） | 该 case 标为「引擎判据无效」 |
| （开发期）检测器只取 argmax 带 | 残留半屏字 | **我们的代码 bug** | v2 已修；已写成注释与 sweep 脚本 |
| （开发期）LaMa 输出白斑 | 全图饱和 | **我们的代码 bug**（后处理多乘 255） | 已修；判定方法写进 docstring |
| （开发期）指标用均值 | 结论反复横跳 | **我们的口径 bug** | v2 中位数 + 剔除近黑帧 |

> **第四类「代码有 bug」是我们自己的责任**，不能推给模型。
> 上面三条就是典型。写进报告比藏起来值钱 —— 面试时讲「我自己的检测器第一版有 bug，
> 怎么定位到是『mask 只覆盖半行字幕』的」比讲任何指标都有说服力。

## 7. 阈值现状（诚实版）

`spec/subtitle_erase.yaml` 里的 30dB / 0.90 是**按行业常识填的初版（C 级）**，
不是业务判断。当前数据表明：

- **30dB**：全宽横带 inpaint 稳定达不到（16–19dB）；换成**逐文字 mask + LaMa** 后
  最好到 **24.66dB**（M1_01），仍未到 30dB。→ 这个阈值要么按实际能力下调，
  要么再加一道「成片观感」判断。**人评工作台已就绪**（`eval/human_review/`），
  打分后由 `summarize` 反推阈值候选 —— 这才是阈值的来源。
- **0.90 SSIM**：全宽带结构上就不可能过（0.40–0.78）；
  **逐文字 mask + LaMa 在 M1_01 达到 0.930** → **这一档是够得着的**。
- **PSNR 对生成式修补器整体不友好**：LaMa 补出来的内容「看起来对」但与原图逐像素不同，
  PSNR/SSIM 会系统性偏低 → **必须配一档人评/感知指标**，不能只靠 PSNR 判生死。
- **区外不误伤**：这条**已被证明可满足**（Δ=0.0，mask 外 99dB）→ 保留为硬约束。

**要用户拍板**：字幕擦除的「可接受」到底是多少 dB / 看不看得出来？
做法（已经备好）：`eval/human_review/make_items.py` 出成片+指标+成本 →
你看片填 `results/human_review/reviews.json` → `summarize` 自动给出阈值候选与达标成本。

## 8. 复现命令

```bash
cd video-dubbing-pipeline
python eval/runner.py --stage subtitle_erase --case-set all --frames 24 \
       --run-id 2026-11-25_erase_v2                 # 跑分 → results/<run_id>/
python eval/runner.py --stage subtitle_erase --case-set all \
       --baseline 2026-11-25_erase_v2                # 回归 diff（只许变好）
python scripts/erase_sweep.py --case M1_04 --frames 24   # 参数扫描（median 口径）
python scripts/erase_compare.py --case M1_04 --frames 8   # 引擎 × mask 粒度 2×2
python scripts/erase_compare.py --case M1_01 --frames 4   # 同上（第二条 case 复现）
python scripts/engine_sanity.py --case M1_04 --frames 4   # 引擎健全性（挖大洞）
python eval/human_review/make_items.py --cases all      # 出人评清单（成片+指标+成本）
python scripts/erase_subtitles.py --video assets/derived/M1_04_hard_sub_bottom.mp4 \
       --gt assets/raw/M1_04.mp4 --out _work/erase/out.mp4   # 出成片（落盘口径）
```

**数字口径纪律**：评测一律**编码前**（`subtitle_erase_in_memory`）、**中位数**、
**剔除近黑帧**；落盘口径只在需要出成片时用，且必须和 baseline 成对报。
