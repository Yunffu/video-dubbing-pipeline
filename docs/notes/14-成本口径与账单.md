# 成本口径与账单（2026-11-25）

> 对应用户第 2 点后半句：「**我评判后我们来计算刚刚使用的成本，在效果可控的时候降低 API 账单**」。
>
> 这句话拆成工程动作是三步，本文件是第 ②③ 步的落地记录：
>
> ```
> ① 记 token      → pipeline/translate/openai_compatible.py（provider 实录）
> ② token→美元   → pipeline/pricing.py（单价表唯一来源）
> ③ 算账 + 找大头 → eval/cost.py（一张表 + 反事实对比）
> ```
>
> **口径纪律**：一个数字只有一个算法，且能指到一条可复跑的命令。

## 0. 结论先说（这是本文件最有价值的一段）

| 环节 | 本项目实际花费 | 反事实（换成 DeepSeek 官方托管 API，list price） |
|---|---|---|
| 翻译 | **$0.00019** / 1.98 分钟音频（$0.0000966/分钟 · $0.0060/千段） | 同上（本项目用的就是它） |
| ASR | **$0**（本地 faster-whisper int8, CPU） | $0.00382（$0.116/小时） |
| TTS | **$0**（edge-tts） | $0.05031（$0.45/万字符） |
| **合计** | **$0.00019** | **$0.05413**（≈ **283×**） |

复跑命令：

```bash
python eval/cost.py --scan results/scenarios
```

→ **成本大头不是翻译，是 ASR + TTS（占反事实账单的 99.6%）。**

> 快照时间 **2026-11-25 20:24**（4 次运行 / 32 段 / 1.98 分钟音频）。
> **总数会漂**（TTS 与翻译的输出非确定性，重跑会变），**费率不会**
> （$/分钟音频、$/千段）→ 引用请用费率，或连同快照时间一起引用。

这条结论直接决定降本该往哪儿使劲：

- ❌ **不值得**为省翻译钱去优化 Prompt / 缩短上下文 —— 那里最多省 $0.00019。
- ✅ **值得**做的是：ASR/TTS 尽量留在本地或自建（我们已经是）、缓存复用、模型分级路由、
  以及**按效果档位决定哪一段值得调贵模型**。

> ⚠️ 数字口径说明（必须一起看，否则会误读）：
> - 这 4 次历史 run 只留了 `total_tokens`，**分不清输入/输出** → 成本按下界计
>   （全算输入价），所以真实翻译成本 **≤ $0.00019**，结论方向不受影响。
> - 单价取自官方定价页（2026-11-25 抓取核实，非记忆）：
>   `https://api-docs.deepseek.com/quick_start/pricing`
> - 反事实用的是 **list price**，不是促销价（官方 TTS/ASR 有限时 5 折）→ 反事实账单偏大，
>   真实差距比 283× 小。这是**保守方向**（对我们有利的那一侧我们没占）。

## 1. 单价表（唯一来源：`pipeline/pricing.py`）

单位：美元 / 百万 tokens。**高峰时段单价 ×2**。

| 模型 | 输入（缓存命中） | 输入（未命中） | 输出 | 备注 |
|---|---|---|---|---|
| `deepseek-flash`（V4.1-Flash-1017） | $0.003 | $0.15 | $0.60 | 官方当前主力便宜档 |
| `deepseek-v4-pro`（V4-Pro-0813） | $0.022 | $0.66 | $1.98 | 贵档 |

高峰时段（官方原文）：**UTC 周一至周五 01:00–04:00 与 06:00–10:00**，不含中国法定节假日；
其余时间（含周末、节假日）全为非高峰。→ 本地 UTC+8 即**工作日 09:00–12:00 与 14:00–18:00**。

**已知简化（如实写出来）**：中国法定节假日我们无法自动判断，所以高峰判定只按星期几算。
需要精确时用环境变量覆盖：`DEEPSEEK_PEAK_OVERRIDE=0`（强制按非高峰）/ `=1`（强制按高峰）。

**旧模型名**：官方文档当前只列 `deepseek-flash` / `deepseek-v4-pro`，并说明旧名
`deepseek-v4-flash` / `deepseek-v4-flash-vision-exp` 由 V4.1-Flash 承载并按 Flash 价计费。
我们配置里默认仍是 `deepseek-chat`（**实测 2026-11-25 本机调用成功**、返回了 usage token），
`pipeline/pricing.py` 把它**按 flash 价**折算。→ 换用现行名更保险，属待办。

## 2. 「这一轮花了多少钱」怎么算（`eval/cost.py`）

```bash
python eval/cost.py --scan results/scenarios            # 账
python eval/cost.py --scan results/scenarios --simulate cache 0.3   # 降本测算
```

输出示例（2026-11-25）：

| run | 段数 | 时长(s) | token(总) | 翻译成本$ | $/分钟 | $/千段 | 后端 | 降级 |
|---|---|---|---|---|---|---|---|---|
| S1_02 | 13 | 37.76 | 430* | 0.00006450 | 0.00010249 | 0.00496154 | deepseek | 否 |
| S1_03 | 9 | 25.84 | 291* | 0.00004365 | 0.00010135 | 0.00485 | deepseek | 否 |
| S2_01 | 5 | 30.0 | 252* | 0.00003780 | 7.56e-05 | 0.00756 | deepseek | 否 |
| S2_03 | 5 | 25.0 | 300* | 0.00004500 | 0.000108 | 0.009 | deepseek | 否 |

合计：4 次运行 · 32 段 · 1.98 分钟音频 · 翻译 **$0.00019**（$0.0000966/分钟音频 · $0.0060/千段）

`带 * = 只留了 total_tokens，成本按下界计`。

三条容易忽略的设计：

1. **失败的钱也算**：`degraded_cost_usd` 单列降级运行花掉的钱，`retried_calls` 单列重试次数。
   一次 5xx 重试 3 次 = 3 份 token，这部分钱不会因为「最终降级成功」而消失。
2. **降级运行的成本照样进账**：本项目 `_work/runs/BV1zGy5ziEnd_00000` 那次是
   **offline 降级**（provider=offline、degraded=true、token=0）→ 翻译 $0，
   但**成品不可对外交付**，所以「省钱」和「可交付」在账上是两列，不能互相抵消。
3. **口径指纹**：token 拆分是精确还是只有总数，行内用 `*` 标；口径不同的两轮成本**不能直接比**。

## 3. 降本三种手段（`--simulate`，给区间不打包票）

| 手段 | 机制 | 估法 | 风险 |
|---|---|---|---|
| `cache` | 命中前缀缓存 / 复用上次结果 | 省下的比例 = 命中率 | 还要扣缓存写入与失效 |
| `batch` | N 段合成 1 次请求 | 省每段的固定指令开销（保守按 prompt 15% 估） | 长 prompt 可能触发 max_tokens 截断 |
| `routing` | 便宜档先跑，难例才升级 | 贵档比例 × 单价差（保守按 50% 估） | 分级判错 → 效果掉档 |

> `simulate` 给的是**区间估计**，不是承诺。原因：命中率、批大小、分级比例都是假设值，
> 没有实测就不许诺。实测口径留在 `--scan` 的真实账单里。

**真实可降的一项（非模拟）**：把批量作业排到**非高峰**时段 → 单价直接打对折。
这是 DeepSeek 侧写死的规则，我们只要不撞上 01–04 / 06–10 UTC 就行，零工程量。

## 4. 已经写进 spec 的成本阈值

`spec/translate.yaml`：

```yaml
- name: 单次请求成本（美元/千段）
  threshold: 0.02
  threshold_source: B-实测（2026-11-25，4 次真实 DeepSeek 调用 32 段）
    实测 $0.00596719/千段（2026-11-25 20:24 快照）；阈值取 3 倍余量
- name: 翻译成本（美元/分钟音频）
  threshold: 0.001
  threshold_source: B-实测（同上；实测 $0.0000966/分钟音频，阈值取约 10 倍余量）

budget:
  cost_usd_per_min_audio: 0.001
  cost_usd_per_1k_segments: 0.02
  peak_hours_utc: [1-4, 6-10]
```

**阈值来源写明「实测」而不是「行业惯例」** —— 这是 `spec/` 的纪律：
阈值必须能指回一条命令和一个口径，否则就是拍脑袋。

## 5. 与「效果判定权在人」的衔接（这才是重点）

成本不能单独优化。**先有人的判定，再有阈值，才谈得上压账单**：

```
人评打分（results/human_review/reviews.json）
   ↓  build_packet.py summarize
指标阈值候选 + 达标样本花了多少 / 不达标样本花了多少
   ↓  写回 spec/*.yaml（注明来源=人评）
成本预算阈值 = 「达标的那部分」的成本
```

`eval/human_review/build_packet.py::summarize` 已经能算出：
- `cost.good_usd` → 达标样本花的钱 = **降本的上限目标**（再省也不能让效果掉出这个成本）
- `cost.bad_usd` → 不达标样本花的钱 = **该砍掉的**（这部分预算直接省下来）

> 当前 `reviews.json` 还是空的（等人评），所以这条链的**最后一环尚未闭合**。
> 已有 `reviews.simulated.json` 用来证明链路通，**但它不是人的判断，不能当结论引用**。
